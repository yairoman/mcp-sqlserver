# ODD · mcp-sqlserver · Ejemplos de uso en el README

## Alcance

Añadir a `README.md` una sección nueva **"Ejemplos de uso"**, en español, con datos ficticios, ubicada después del catálogo de tools. Sirve para que quien instale el servidor MCP vea cómo se usa en la práctica. Solo documentación: no se toca código.

## Tareas

1. Revisar el catálogo de tools del `README.md` y el código de `src/tools/{schema,data,query,performance,integrity}/` (definiciones, `inputSchema` y formato de salida con `src/utils/result-formatter.ts`).
2. Definir una base ficticia `TiendaDemo` (por ejemplo, tablas `dbo.Clientes`, `dbo.Productos`, `dbo.Pedidos` y `dbo.DetallePedidos`) y describirla brevemente al inicio de la sección.
3. Escribir un ejemplo por categoría (esquema, datos, consulta, rendimiento, integridad): entre 5 y 8 ejemplos. Cada uno lleva:
   - lo que el usuario le pide al LLM (conversación);
   - qué tool se llama y con qué argumentos (JSON válido según su `inputSchema`);
   - una salida ilustrativa con el mismo formato que produce la tool.
4. Cerrar con un flujo corto de auditoría de rendimiento (3–5 pasos encadenando tools reales del catálogo).
5. Marcar las salidas como "ejemplo ilustrativo (datos ficticios)".
6. Añadir la entrada al índice o tabla de contenidos del README, si existe.

## Criterios de terminado

- `README.md` contiene la sección `## Ejemplos de uso`, situada después del catálogo de tools.
- Hay al menos un ejemplo por cada una de las 5 categorías y un flujo de auditoría al final.
- Todo nombre de tool usado en los ejemplos existe en `src/server.ts` (comprobado con grep tool por tool) y sus argumentos coinciden con el `inputSchema` (nombres de parámetro reales).
- Los bloques JSON de argumentos son JSON válido (comprobado con `python3 -m json.tool` o `jq`).
- Las consultas SQL de ejemplo pasan las reglas de `sql-sanitizer.ts`: empiezan por `SELECT`/`WITH`, sin `--`, `/*` ni palabras vetadas.
- Comprobación de datos sensibles: grep sin hosts reales, IPs, contraseñas, tokens ni nombres de clientes; nada copiado de `docs/` ni de `.env`. Solo se usan `TiendaDemo`, `localhost` y credenciales de marcador (`<tu_usuario>`).
- `git diff --stat` muestra solo cambios en `README.md`.
- `npm test` / `npm run lint`: no aplican a un cambio de documentación y **no se pueden verificar** (no hay Node en el entorno). Queda anotado en el PR.
- Trabajo en la rama `odd/T-<n>`, con un PR abierto hacia `main` y Conventional Commits (`docs: …`). Sin merge.

## Fuera de alcance

- Ejemplos de las 33 tools una por una.
- Usar AdventureWorks, WideWorldImporters o cualquier dato real.
- Archivo de ejemplos aparte.
- Cambios de código, tests, `CLAUDE.md` o skills.
- Ejecutar los ejemplos contra un SQL Server real.

## Decisiones ya tomadas

- Tipo de ejemplos: conversación (principal) más llamada directa a la tool con su JSON (Yair: "adelante" a la propuesta 1C).
- Cobertura: uno por categoría (5–8) más un flujo corto de auditoría (2A+C).
- Datos: base inventada `TiendaDemo` (3A).
- Salidas ilustrativas armadas a partir del código, marcadas como tales (4A).
- Sección dentro de `README.md`, en español, después del catálogo (5A).
- Sin credenciales, variables de entorno ni servicios externos.
- Si el README no tiene catálogo identificable, la sección va antes de la de configuración de clientes MCP o al final, y se anota en el PR.
- Si se bloquea, se marca la tarea como bloqueada en vez de improvisar.
