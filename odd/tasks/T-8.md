# ODD · mcp-sqlserver · Diagrama de proceso del flujo de una consulta

## Alcance

Generar con la skill **diagram-design** (https://github.com/cathrynlavery/diagram-design), tipo **Process** (secuencia con varios actores), un diagrama del flujo de una consulta en el servidor MCP: desde la petición del LLM hasta el resultado formateado, pasando por la tool, `sql-sanitizer`, `MSSQL_READ_ONLY`, el pool `mssql` y SQL Server. Queda en `assets/diagramas/`, enlazado desde `README.md`. Solo documentación, sin cambios de código.

## Tareas

1. Obtener la skill diagram-design (`skills/diagram-design/`: `SKILL.md`, `references/`, `assets/`) y seguir su guía para el tipo **Process**, variante minimal claro.
2. Leer el código real para que el diagrama sea fiel: `src/server.ts` (registro de las tools), un handler de consulta en `src/tools/query/`, `src/utils/sql-sanitizer.ts`, `src/config.ts` (`MSSQL_READ_ONLY`), `src/connection.ts` (pool diferido) y `src/utils/result-formatter.ts`/`error-handler.ts`.
3. Actores (columnas): Usuario · LLM / cliente MCP · Servidor MCP (STDIO) · Validación (sanitizer + solo lectura) · Pool `mssql` · SQL Server. Pasos: petición → llamada a la tool por JSON-RPC → validación de argumentos → sanitizer (rechazo con error si falla) → comprobación de solo lectura → conexión diferida del pool en la primera consulta → ejecución → formato del resultado → respuesta al LLM → respuesta al usuario. Incluir la rama de rechazo como desvío claro.
4. Guardar `assets/diagramas/flujo-consulta.html` (HTML autocontenido con SVG inline) y `assets/diagramas/flujo-consulta.svg`.
5. Añadir en `README.md` una mención breve con el enlace al diagrama (en la sección de arquitectura o de seguridad si existe; si no, justo antes de "Ejemplos de uso").

## Criterios de terminado

- Existen `assets/diagramas/flujo-consulta.html` y `assets/diagramas/flujo-consulta.svg`.
- El `.html` es autocontenido: sin `<script src=`, sin imágenes externas ni CDN (grep de `http` solo en atributos xmlns/enlaces de texto). El `.svg` es XML válido (`python3 -c "import xml.dom.minidom,sys;xml.dom.minidom.parse(sys.argv[1])"`).
- Si la skill trae verificadores ejecutables sin Node (scripts Python como lint de skin/render/geometría), se corren sobre el `.html` y se reporta la salida; los que requieren Node o navegador quedan **no verificados**.
- Cada nombre de archivo, función, variable o tool que aparece en el diagrama existe en el repo (grep uno por uno).
- Comprobación de datos sensibles: sin hosts, IPs, contraseñas, tokens ni nombres de clientes; nada de `docs/` ni de `.env`. Si hace falta un ejemplo, se usa `TiendaDemo`.
- `git diff --stat` muestra solo `assets/diagramas/*` y `README.md`; nada en `docs/`.
- `npm test` / `npm run lint`: no aplican a este cambio y **no se pueden verificar** (no hay Node). Queda anotado en el PR.
- Trabajo en la rama `odd/T-<n>`, con un PR abierto hacia `main` y Conventional Commits (`docs: …`). Sin merge.
